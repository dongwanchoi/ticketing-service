# 스키마 누락·위험 및 개선 후보 — 1차

2026-10-28, 기준 dev `00a07d7db796e86e3f22f46d8d5bb9e0aa3d11ca`.
증거와 전체 매핑은 [현황 분석](current-schema-analysis.md)을 따른다. **후속 조사에서 MySQL TCP 직접 접근에 성공**했다. Docker 권한 문제는 유지된다. 아래 초기 소스 분석의 미확인 표현은 마지막 「실제 스키마 대조 확정 결과」의 실측 범위에 한해 갱신된다. 제안은 승인 전 검토 후보이며 새 ERD나 구현 지시가 아니다.

## 확인한 차이와 미확인 차이

| 분류 | 확인한 사실 | 영향/검토 후보 |
|---|---|---|
| 저장소 DDL ↔ JPA | auth-schema.sql의 USER CHECK, ascii/ascii_bin이 AppUser 매핑에 없음 | Hibernate 생성 테스트 스키마와 수동 DDL이 동등하다고 볼 수 없음. 실제 DDL 수집 후 마이그레이션·스키마 검증 기준 통일 |
| DTO ↔ JPA | 판매 status는 DTO @NotNull, entity에는 NOT NULL 선언 없음 | HTTP 외 경로/직접 DB 쓰기의 불변조건 범위 검토 |
| 서비스 ↔ entity | 판매 기간 짝/순서, 동일 공연장, 양수 가격 검증이 엔티티/DB까지 모두 표현되지 않음 | 저장 경로마다 보장하는 규칙을 분리해 정의하고 제약·도메인 검증 적용 후보화 |
| 정책 ↔ 구현 | Buyer/Seller/Admin·검수/소유권 요구, 현재 USER만 생성·관계 없음 | 역할·판매자 소유·검수 수명주기 재설계 필요 |
| 응답 이름 ↔ 집계 의미 | remainingSeatCount = 모든 SessionSeat 개수 | 예매 도입 시 재고 상태를 반영해야 함. 현재 API를 실제 잔여로 신뢰하면 위험 |
| 실제 DB ↔ JPA | 후속 metadata/무결성 집계 성공 | 7테이블·6FK·4UNIQUE 대응. 회원 collation/CHECK는 실제 DB에 존재하나 JPA 미명시. 아래 확정 결과 참조 |

## 우선순위별 정합성 위험

P0는 예매 구현 전 해결할 핵심 불변조건, P1은 재설계/이행 전 확인, P2는 측정 후 정리 후보다. 현재 미구현 기능에 이미 운영 장애가 발생했다는 의미는 아니다.

| P0 | 선점/예매/결제 모델·명령 API 부재 | 실패·타임아웃·재시도·늦은 결제 성공 처리 없음 | 만료 직전 확정/재선점 경쟁, 실패 해제, 중복/역순 결과, 롤백 |

| P1 | 전체 엔티티에 생성/수정/삭제·감사 이력 없음 | 업무 시각과 감사 시각 분리 필요. 단순 updatedAt만으로 상태 전이 이력 복원 불가 | 필요한 도메인별 이력·보존·접근 권한 기준 |
| P1 | 물리 삭제 호출·연쇄 정책 미정 | 판매 후 삭제 시 참조/증빙 보존 위험. 실제 FK 삭제 규칙 미확인 | 부모 삭제/거래 참조 시 금지·취소·보존 규칙 |
| P1 | LocalDateTime/한국 현재시각, DB timezone 미확인 | 만료·판매 경계 시간 기준 혼용 위험 | 저장/비교/표시 시각·정밀도·Clock 전략 |
| P1 | 수동 CREATE TABLE, 생성 스키마 테스트 중심 | 이력형 마이그레이션과 기존 데이터 사전 검증·롤백 검증 부재 | 실제 DDL baseline, 비파괴 이행 리허설 |

소스에서 없는 개념이 실제 DB에도 없다고 단정하지 않는다. DB 단독 제약·트리거·별도 테이블은 미확인이다.

## 중요한 설계 쟁점 — 사용자 결정 필요

아래는 확정안이 아니다. 먼저 실제 DDL 확보를 마친 뒤 순서대로 결정한다.

1. **선점과 확정 예매의 수명주기**: SessionSeat에 현재 점유 상태를 두는 방식과 별도 선점/거래 이력을 두는 방식, 또는 혼합을 비교한다. 선점 단위(1좌석/묶음), TTL, 만료 후 결제 성공, 확정 후 취소·재판매 허용 여부가 선행 정책이다.
2. **경쟁 통제**: 조건부 UPDATE는 영향 행 수·조건의 완전성이 중요하고, 비관적 락은 대기/데드락·트랜잭션 길이가 비용이며, 낙관적 락은 고경합 재시도 부담이 있다. 특정 방식을 지금 확정하지 않는다. 다중 좌석 원자성과 DB 보장 조건도 함께 비교한다.
3. **역할·소유권·검수**: 사용자 한 명의 복수 역할 여부, 판매자 승인/회수, 공연 소유 변경, 검수 후 수정의 재승인·판매 중단 기준을 정한다.
4. **판매·가격**: 기간 없는 OPEN을 허용할지, 승인/회차 시작과 판매 종료의 관계, 무료 좌석 여부, 통화/금액 정밀도 및 예매 당시 가격 보존을 결정한다.
5. **취소·삭제·이력**: 공연/회차/회원의 삭제와 거래 증빙·개인정보 보존 관계, 만료/취소/실패 이력 최소 보존과 감사 접근권한을 정한다. 일괄 soft delete를 기본값으로 삼지 않는다.
6. **시간과 멱등성**: 저장 시각 기준·만료 판정의 권위 시계·경계 정밀도, 중복 요청 키 범위/수명 및 결제 재시도 정책을 정한다.

## 다음 조사 및 이행 범위

- 후속 직접 TCP 조사로 현재 계정이 볼 수 있는 DB metadata와 무결성 집계를 확인했다. Docker 컨테이너 동일성의 독립 확인과 SHOW CREATE/권한 범위 검증은 남아 있다.
- 실제 스키마와 JPA를 컬럼/제약/인덱스 단위로 대조하고, 개인정보 없는 집계로 중복·고아·공연장 불일치·가격·기간 오류를 확인한다.
- 그다음 기존 정책과 사용자 결정을 바탕으로 대안 2~3개, 비용·실패 조건·이행/롤백 계획·재현 가능한 동시성 테스트 계획을 제시한다. 기존 구조의 전체 폐기나 새 ERD 확정은 선행하지 않는다.
- 영향 범위: 엔티티/DDL·repository SQL·서비스 트랜잭션·SecurityConfig/principal·DTO/API·프런트 잔여/가격 표시·fixture·통합/경쟁 테스트·시드 도구. 이번 단계에서는 어느 것도 변경하지 않았다.

핵심 원리: 행의 등록 중복을 막는 UNIQUE와, 만료·소유권·상태 전이를 포함한 중복 판매 방지는 서로 다른 불변조건이다.

## 실제 스키마 대조 확정 결과 — 2026-10-28 후속

### 실제 확인한 사실

- Compose의 로컬 포트 3307과 infra/.env 접속 설정을 사용해 `ticketing_service` MySQL 8.4.11에 직접 접속했다. 비밀값은 출력·문서화하지 않았다. Docker 컨테이너와의 런타임 동일성 확인은 접근 제한으로 남아 있다.
- 실테이블 7개, PK 7개, FK 6개, PK 외 UNIQUE 4개, CHECK 1개, 인덱스 총 14개다. 관계와 유일성은 JPA 선언과 대응한다. 모든 FK 참조 규칙은 NO ACTION으로 자동 삭제 cascade가 없다.
- `app_user.username`은 ascii/ascii_bin이고 `ck_app_user_role(role='USER')`는 ENFORCED=YES다. 수동 DDL과 일치하지만 JPA에는 두 항목이 없다. 따라서 Seller/Admin 도입은 애플리케이션 역할 확장만으로 완료할 수 없다.
- `performance_sale.status`는 실제 NULL 허용이다. JPA와 일치하므로 매핑 불일치가 아니라 업무 제약 강화 후보다. 조회 시점 NULL 데이터는 0건이다.
- 실제 `price decimal(38,2)`, 시각 `datetime(6)`, enum native 타입을 확인했다. JPA 미명시 사항을 실제 타입 차이라고 단정하지 않고 명시적 기준·이식성 개선 후보로 분류한다.
- 판매 기간 짝/순서·가격 양수·좌석번호 양수 CHECK는 없다. 공연장 동일성은 독립 FK만으로 강제되지 않는다. 관련 무결성 집계는 각각 0건이며 현존 데이터 손상은 발견하지 않았다.
- 각 FK 고아와 복합 중복 그룹은 0건이다. 판매 정책 없는 공연은 1건으로 현재 코드상 판매 불가이며, 강제 정책 존재를 요구할지는 사용자 결정사항이다.
- 조회 가능한 선점/예매/결제/감사 테이블, 상태·만료·version 컬럼은 없다. 가시 trigger/event/view도 각각 0개지만 계정의 metadata 가시성 밖 객체는 단정하지 않는다.

### 유지/수정 분류 갱신

| 분류 | 실제 근거 | 제안 |
|---|---|---|
| 유지 가능 | 물리좌석/회차좌석 UNIQUE와 6FK 실제 존재, 고아·중복·공연장 불일치 0 | 구조를 폐기할 근거 없음. 재설계 시 기존 키와 참조를 보존하는 방안 우선 |
| 수정 후보 | 실제 USER-only CHECK + JPA 미표현 | 역할 정책 결정 후 제약·인증·테스트 스키마를 함께 이행 |
| 수정 후보 | status nullable, 가격/기간 CHECK 없음 | 기존 무효 데이터 0건을 사전 근거로 삼되 경쟁 쓰기·실제 운영 영향 검토 후 강화 |
| 수정 후보 | FK NO ACTION, 삭제 서비스는 물리 삭제 | 참조 있는 부모 삭제의 처리/오류 응답 및 거래 보존 정책 정의 |
| 명시 후보 | decimal(38,2), datetime(6), native enum, collation | 허용 범위·시간/통화·정렬/비교 정책을 명시하고 마이그레이션 baseline으로 관리 |
| 신규 검토 | 실스키마에도 선점·예매·결제 구조 없음 | 선점/거래 수명주기·멱등성과 최소 이력 설계는 필요하지만 ERD는 미확정 |
| 성능 미결정 | 기존 PK/UNIQUE/FK용 인덱스 전수 확인 | EXPLAIN/부하 측정 전 추가 복합 인덱스 필요성을 확정하지 않음 |

### 여전히 확인하지 않은 것

Docker 런타임 컨테이너 동일성, SHOW CREATE 원문과 기본값 표현의 차이, 계정 권한 밖 객체, 실제 다중 요청/결제/만료 경쟁, 쓰기 시 DB 제약 거절 응답, 실행계획·성능, 재설계 마이그레이션 안전성은 미검증이다. 이번 건수 정상 결과만으로 예매 정합성을 증명하지 않는다.
